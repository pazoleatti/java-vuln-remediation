# Конвейер ремедиации SAST — инструкция оператора

Запуск конвейера автоматической ремедиации уязвимостей корпоративного SAST из qwen cli, прямо в корне вашего Java-проекта. После прогона вы получаете отдельную git-ветку с одним коммитом на каждый фикс и markdown-отчёт с обоснованиями отклонений и инструкциями для регрессионного тестирования.

---

## 1. Что вы получите за один прогон

- Новую git-ветку `sast-fix/<commit>-<runId>` с N коммитами (по одному на каждое подтверждённое исправление).
- Файл `sast-report-<runId>.md` в корне рабочего дерева (намеренно **не закоммичен** — это материал для вашего ревью, а не для MR).
- Файл состояния `.sast-agent/state.json` со всеми решениями агентов.

После ревью отчёта и diff'ов вы сами пушите ветку и открываете MR.

---

## 2. Предусловия

| Что нужно | Как проверить |
|---|---|
| Node.js ≥ 18 | `node --version` |
| qwen cli установлен | `qwen --version` |
| Доступ к корпоративному SAST API (URL + JWT-токен) | спросите у безопасников |
| Внешний MCP `code-index` сконфигурирован в qwen | без него прогон прерывается на старте |
| Java-проект под git, рабочее дерево чистое | `git status` без правок |

## 3. Установка (делается один раз)

### 3.1. Сборка MCP-серверов

В **отдельном** каталоге (не в вашем рабочем проекте):

```bash
git clone https://github.com/Neovaryag/java-vuln-remediation.git
cd java-vuln-remediation
npm install
npm run build
```

Запомните абсолютный путь к этой папке — он понадобится в конфиге qwen. Далее везде `<MCP_DIR>` означает этот путь.

### 3.2. Размещение agents / commands / skills

Чтобы slash-команда `/sast-run` и Named Subagents были доступны **в любом** вашем проекте, скопируйте конфигурацию qwen из репозитория MCP в ваш домашний `~/.qwen/`:

**Linux / macOS:**
```bash
mkdir -p ~/.qwen/agents ~/.qwen/commands ~/.qwen/skills
cp -r <MCP_DIR>/.qwen/agents/*    ~/.qwen/agents/
cp -r <MCP_DIR>/.qwen/commands/*  ~/.qwen/commands/
cp -r <MCP_DIR>/.qwen/skills/*    ~/.qwen/skills/
```

**Windows (PowerShell):**
```powershell
$qwen = "$HOME\.qwen"
New-Item -ItemType Directory -Force -Path "$qwen\agents","$qwen\commands","$qwen\skills" | Out-Null
Copy-Item -Recurse -Force <MCP_DIR>\.qwen\agents\*    "$qwen\agents\"
Copy-Item -Recurse -Force <MCP_DIR>\.qwen\commands\*  "$qwen\commands\"
Copy-Item -Recurse -Force <MCP_DIR>\.qwen\skills\*    "$qwen\skills\"
```

> Альтернатива: положить эти три каталога в `.qwen/` корня **каждого** проекта, который будете чинить. Глобальный путь удобнее, если проектов несколько.

### 3.3. Конфигурация MCP-серверов в qwen

Откройте настройки qwen (`~/.qwen/settings.json`) и добавьте в блок `mcpServers` четыре сервера:

```json
{
  "mcpServers": {
    "sast-remediation-mcp": {
      "command": "node",
      "args": ["<MCP_DIR>/dist/servers/sast/index.js"],
      "env": {
        "SAST_API_BASE_URL": "https://sast.your-corp.example",
        "SAST_JWT_FILE": "/absolute/path/to/sast-jwt.txt"
      }
    },
    "sast-report-state-mcp": {
      "command": "node",
      "args": ["<MCP_DIR>/dist/servers/report/index.js"]
      // если задаёте SAST_CACHE_DIR ниже — продублируйте сюда тот же путь
    },
    "repo-mcp": {
      "command": "node",
      "args": ["<MCP_DIR>/dist/servers/repo/index.js"]
    },
    "code-index": {
      "command": "...",
      "args": ["..."]
    }
  }
}
```

Замечания:

- `<MCP_DIR>` замените на абсолютный путь. На Windows — с двойными `\\` (например, `C:\\Users\\you\\java-vuln-remediation`).
- `SAST_API_BASE_URL` обязателен — без него SAST-сервер не стартует.
- `SAST_JWT_FILE` (путь к файлу с токеном) предпочтительнее `SAST_JWT` (токен инлайн): файл перечитывается при каждом вызове, ротация без рестарта qwen.
- `SAST_CACHE_DIR` — **необязательный** путь к каталогу кэша SAST-отчётов. По умолчанию `<os.tmpdir()>/sast-mcp-cache` (на Windows — `%TEMP%\sast-mcp-cache`, на Linux/macOS — `/tmp/sast-mcp-cache`). Если задаёте кастомный путь — задавайте его **обоим** серверам, `sast-remediation-mcp` **и** `sast-report-state-mcp`, и **одинаковый**: первый туда пишет отчёт на `get_report`, второй читает оттуда же на `init_run`. Расхождение приведёт к ошибке «no cached SAST report for commit …».
- `SAST_AGENT_STATE_DIR` — необязательный путь к каталогу state-файла `state.json`. По умолчанию `.sast-agent/` в текущем рабочем дереве — этого обычно достаточно.
- `code-index` — внешний MCP, его конфиг возьмите из его собственной документации.
- Для `repo-mcp` переменные окружения не нужны.

### 3.4. Проверка

Запустите `qwen` в любом каталоге и убедитесь, что:

- `/sast-run`, `/sast-list`, `/sast-cache-clear` появляются в автодополнении slash-команд;
- в списке доступных tools видны `mcp__sast-remediation-mcp__*`, `mcp__sast-report-state-mcp__*`, `mcp__repo-mcp__*`, `mcp__code-index__*`.

## 4. Прогон в вашем проекте

### 4.1. Подготовка проекта

```bash
cd /path/to/your/java-project
git status              # должно быть clean
git fetch && git checkout <ветка-для-починки>
```

Зафиксируйте git-хеш HEAD — он же должен быть `--commit` в SAST-сканировании:

```bash
git rev-parse HEAD
```

### 4.2. Запуск qwen

```bash
qwen
```

qwen стартует в интерактивном режиме в текущей директории.

### 4.3. Ввод slash-команды

```
/sast-run --commit=<git-хеш> --nexus=<url-дистрибутива> --jira=<JIRA-KEY> [--limit=<N>] [--include-notexploit] [--vuln=<vulnerabilityHash>]
```

Параметры:

| Флаг | Обязательный | Описание |
|---|---|---|
| `--commit=<хеш>` | да | Полный git-хеш коммита, на котором запущен SAST-скан. Должен совпадать с `HEAD` (или быть его предком). |
| `--nexus=<url>` | да | URL дистрибутива в Nexus, который сканировался. |
| `--jira=<KEY>` | нет (но обязателен для коммитов) | Тикет JIRA в формате `PROJ-1234`. Если не передать — оркестратор сам спросит перед фазой фикса. Без него коммитить нельзя. |
| `--limit=<N>` | нет | Положительное целое. Ограничивает число обрабатываемых уязвимостей за прогон. Подробности в §5. |
| `--include-notexploit` | нет | Булевый флаг (без `=значение`). По умолчанию **выключен** — уязвимости с решением SAST `decision.type == "notexploit"` исключаются из триажа и фикса и попадают в отдельную секцию отчёта. С флагом — такие уязвимости проходят триаж как обычные. Подробности в §6. |
| `--vuln=<vulnerabilityHash>` | нет | Точечный режим: за прогон обрабатывается ровно одна уязвимость с указанным `vulnerabilityHash`. Сильнее `--include-notexploit` (целевая уязвимость всегда триажится, даже если по ней `notexploit`). `--limit` в этом режиме игнорируется. Подробности в §7. |

### 4.4. Что происходит дальше

Оркестратор сам последовательно:

1. Запрашивает SAST-отчёт (`request_report` → опрос `get_report`, до 20 минут). Если отчёт уже в кэше `sast-remediation-mcp` — отдаётся мгновенно без обращения в API. Сброс — через `/sast-cache-clear` (см. §8.1).
2. Засеивает все уязвимости в `.sast-agent/state.json`. По умолчанию `pending`; уязвимости с уже зафиксированным в SAST решением `notexploit` сразу получают статус `skipped_notexploit` и в дальнейшие фазы не попадают (если не передан `--include-notexploit`). В точечном режиме (`--vuln`) засеивается ровно одна уязвимость с указанным `vulnerabilityHash`.
3. Создаёт ветку `sast-fix/<commit>-<runId>` и переключается на неё.
4. Строит индекс кода (`code-index.build_deep_index`).
5. **Триаж**: для каждой уязвимости в порядке убывания severity запускается изолированный `triage-agent`. Вердикт — `confirmed` либо `rejected` с обоснованием.
6. **Фикс** (только после триажа): для каждой `confirmed` строго последовательно запускается `fix-agent` — правит код, делает один атомарный коммит с сообщением, ссылающимся на JIRA.
7. **Финальный отчёт**: оркестратор сам рендерит `sast-report-<runId>.md`.

Внутри прогона взаимодействия с вами **нет** (кроме запроса JIRA-ключа, если вы его не передали). Все отказы и провалы фиксов попадут в финальный отчёт — не пугайтесь, что что-то «молча отвалилось».

Прогон может длиться от минут до часов — в зависимости от числа уязвимостей.

## 5. Параметр `--limit=<N>` — как использовать

### 5.1. Когда применять

- Большой отчёт (десятки/сотни уязвимостей), хочется сначала прогнать самые критичные и оценить качество фиксов.
- Нужно вписаться в ограниченное окно времени.
- Дробить работу на несколько MR'ов (по 5–10 фиксов в каждом для удобства ревью).

### 5.2. Как работает

1. После сортировки списка `pending` (severity DESC → expirationDate ASC) берутся **первые N** записей.
2. Только они уходят в фазу триажа и далее в фикс.
3. Остальные **остаются в `pending`** в `.sast-agent/state.json` и попадают в финальный отчёт в секцию **Skipped (--limit)**.
4. `init_run` всегда засеивает **все** уязвимости из отчёта — состояние полное, агрегаты в отчёте корректны. `--limit` применяется на фазе триажа, не на засеивании.

Пример:

```
/sast-run --commit=abc123 --nexus=https://nexus/.../app.jar --jira=SEC-42 --limit=5
```

Из, скажем, 30 уязвимостей будут обработаны 5 топовых; в отчёте появится секция со списком 25 отложенных.

### 5.3. Как продолжить в следующем прогоне

Чтобы дотриажить остаток — **новый прогон** с тем же `--commit`/`--nexus`. Повторный `init_run` идемпотентен по `(sastUuid, vulnerabilityHash)`: статусы из прошлого прогона сохранятся, а оставшиеся `pending` будут обработаны:

```
/sast-run --commit=abc123 --nexus=https://nexus/.../app.jar --jira=SEC-42 --limit=5
```

Важно: `runId` будет новый → создастся **новая ветка** `sast-fix/abc123-<новый-runId>`. Фиксы из предыдущего прогона остаются в первой ветке. Если хотите все фиксы в одной ветке — мержите ветки сами после прогонов или не используйте `--limit`.

### 5.4. Граничные случаи

- `--limit=0`, отрицательное, нечисловое — прогон прерывается на префлайте.
- `--limit=N` больше числа уязвимостей — лимит неявно игнорируется (обрабатываются все).
- Без `--limit` — обрабатывается весь отчёт.

## 6. Параметр `--include-notexploit` — как использовать

### 6.1. Что это за уязвимости

В корпоративном SAST у уязвимости в `resultInfo[].vulnerabilities[]` может быть проставлено поле `decision`:

```jsonc
{
  "type":       "notexploit",   // прошлое решение корп-системы
  "comment":    "...",
  "author":     "...",
  "createDate": "..."
}
```

`notexploit` означает: «корп-система раньше уже разобрала эту находку и отметила её как ложное срабатывание». По умолчанию мы доверяем этому решению и **не гоняем по таким уязвимостям ни триаж, ни фикс** — это экономит время и сохраняет аудит-историю SAST.

### 6.2. Поведение по умолчанию (флаг **не** передан)

1. На фазе `init_run` уязвимости с `decision.type == "notexploit"` сразу получают статус `skipped_notexploit`.
2. Они не попадают ни в `list_by_status('pending')`, ни в `list_by_status('confirmed')` — триаж- и фикс-агенты их не видят.
3. В финальный отчёт они идут в отдельную секцию **Skipped (notexploit)** с автором, датой и комментарием из SAST.
4. В git-ветке коммитов по ним нет.

### 6.3. Поведение с флагом `--include-notexploit`

```
/sast-run --commit=abc123 --nexus=... --jira=SEC-42 --include-notexploit
```

1. На фазе `init_run` все уязвимости (включая `notexploit`) получают статус `pending`.
2. Они проходят обычный триаж. `triage-agent` обязан **независимо** оценить уязвимость и явно указать в `triageReasoning`, **согласен** ли он с прошлым `notexploit`-решением и почему.
3. Если триаж говорит `confirmed` — уязвимость идёт в фикс на общих основаниях. Если `rejected` — уходит в секцию **Rejected** с собственным обоснованием агента.
4. Исходное решение SAST в любом случае сохраняется на записи в поле `decision` и видно через `get_vulnerability_state`.

### 6.4. Когда применять флаг

- Перепроверка прошлых вердиктов после смены команды безопасности или политики компании.
- Подозрение, что часть `notexploit`-меток устарела (код менялся, добавились новые входные точки, появилось новое окружение).
- Аудит: хочется иметь независимое мнение по всему отчёту, а не только по «свежим» findings.

### 6.5. Граничные случаи

- `--include-notexploit=true`, `--include-notexploit=value` — флаг **не принимает значение**, прогон прерывается на префлайте.
- Уязвимость без `decision` — флаг на неё не влияет, она и так попадает в `pending`.
- Совмещение с `--limit`: лимит применяется **после** разделения на `pending`/`skipped_notexploit`. Без флага `notexploit`-уязвимости не занимают слотов лимита; с флагом — занимают наравне со всеми, и часть из них может попасть в **Skipped (--limit)**, если их severity ниже.

## 7. Параметр `--vuln=<vulnerabilityHash>` — точечный режим

### 7.1. Что это

Точечный режим — прогон конвейера ровно по одной уязвимости из отчёта. Полезен, когда:

- надо разобрать конкретный finding (например, после ревью или по запросу безопасников),
- хочется быстро проверить качество фикса/триажа на одном кейсе перед массовым прогоном,
- нужно перепроверить уязвимость, которую SAST пометил `notexploit`, но без рассмотрения остальных таких уязвимостей.

### 7.2. Где взять `vulnerabilityHash`

Выполните вспомогательную команду `/sast-list` — она печатает таблицу всех уязвимостей в отчёте без триажа и фиксов (см. §8.2). Хеш — первая колонка.

```
/sast-list --commit=abc123
```

Альтернатива — открыть JSON отчёта в кэше `sast-remediation-mcp` и поискать поле `resultInfo[].vulnerabilities[].vulnerabilityHash`. Это рабочий fallback, но `/sast-list` удобнее.

### 7.3. Как работает

1. Оркестратор получает SAST-отчёт как обычно (с использованием кэша).
2. Передаёт `targetVulnHash=<hash>` в `init_run`. `sast-report-state-mcp` читает отчёт из кэша по коммиту, ищет в `resultInfo[].vulnerabilities[]` запись с этим хешем и засеивает только её. Если такой нет — `init_run` возвращает `targetFound: false`, прогон прерывается до создания ветки и индекса.
3. В точечном режиме `init_run` принудительно игнорирует фильтр `notexploit` — целевая уязвимость всегда попадает в `pending`, даже если у неё `decision.type == "notexploit"`.
4. Создаётся ветка, строится индекс, делегируется ровно один `triage-agent`, затем (если `confirmed`) — один `fix-agent`. Всё как в обычном прогоне, но для одной уязвимости.
5. В финальном отчёте — ровно одна запись в одной из секций (`Rejected`, `Fixed`, `Fix failed` или `Obsolete`). Секция **Skipped (notexploit)** в точечном режиме отсутствует.

Пример:

```
/sast-run --commit=abc123 --nexus=https://nexus/.../app.jar --jira=SEC-42 --vuln=h7f3a2b1c
```

### 7.4. Взаимодействие с другими флагами

- `--include-notexploit` — **игнорируется**. В точечном режиме целевая уязвимость всегда триажится, даже если SAST пометил её как `notexploit`. Исходное решение SAST сохраняется на state-записи в поле `decision` и доступно `triage-agent` как контекст.
- `--limit` — **игнорируется** (точечный режим по определению ограничен одной уязвимостью).
- `--jira` — обязателен, как и в обычном прогоне (нужен для commit message, если триаж даст `confirmed`).

### 7.5. Граничные случаи

- `--vuln` без значения или с пустой строкой — прогон прерывается на префлайте.
- Указанный `vulnerabilityHash` отсутствует в отчёте — прогон прерывается **до** создания ветки и построения индекса.
- Триаж может вернуть `rejected` — это валидный исход. Точечный режим не означает «фикс любой ценой».
- Если `triage-agent` дал `rejected`, фаза фикса не запускается, в отчёте будет одна запись в секции **Rejected**.

## 8. Вспомогательные команды

### 8.1. `/sast-cache-clear` — сброс кэша SAST-отчётов

`sast-remediation-mcp` кэширует полученные отчёты по hash коммита. TTL у кэша **нет** — один раз получив отчёт по коммиту `X`, при последующих `/sast-run --commit=X` он будет возвращаться из кэша до явной инвалидации.

Когда нужно сбросить:

- SAST-команда перезапустила скан на тот же коммит (изменились правила/версия движка).
- Подозреваете, что кэш устарел.

```
/sast-cache-clear                    # очистить весь кэш
/sast-cache-clear --commit=abc123    # очистить только конкретный отчёт
```

Команда не запускает оркестратор и не делегирует ничего — это одна обёртка вокруг `sast-remediation-mcp.clear_cache`.

### 8.2. `/sast-list` — таблица уязвимостей в отчёте

Печатает компактную таблицу уязвимостей по hash коммита. Без триажа, без фиксов, без записи на диск. Используется для подбора `--vuln` перед запуском точечного `/sast-run`.

```
/sast-list --commit=abc123
```

Колонки: `vulnerabilityHash`, `severity`, `code`, `location`, `decision`. Сортировка — по severity убывающая.

Если отчёт уже в кэше — мгновенно. Если нет — `sast-remediation-mcp` сходит в API и закэширует, следующий `/sast-run` для этого же коммита будет использовать тот же кэшированный отчёт.

## 9. Финальный отчёт `sast-report-<runId>.md`

Структура (имена секций — как они появятся в файле):

| Секция | Что внутри |
|---|---|
| **Header** (шапка) | runId, commit, исходная ветка, ветка-фикс, reportUuid, JIRA, применённый `--limit` (или `n/a (targeted)`), флаг `--include-notexploit` (или `n/a (targeted)`), `--vuln` (целевой `vulnerabilityHash` или `unset`), гистограмма по severity, итоги (включая `skipped_notexploit`). |
| **Rejected** (отклонённые) | По одной записи на отклонённый finding: id, локация, CWE, severity и **полное обоснование** triage-агента (verbatim — это аудит-артефакт). |
| **Fixed** (исправленные) | id, хеш коммита, краткое описание фикса, инструкция для регрессионного тестирования. |
| **Fix failed** (провалы) | id, локация, CWE, причина провала. Это ваш список ручных доработок. |
| **Obsolete** (устаревшие) | findings, которые в текущем дереве уже неактуальны. |
| **Skipped (--limit)** (отложенные) | Только если применялся `--limit` и есть отложенные. Список того, что не успели в этом прогоне. |
| **Skipped (notexploit)** (исключённые SAST-решением) | Только если флаг `--include-notexploit` **не** передан, прогон **не** в точечном режиме и в отчёте есть `decision.type == "notexploit"`. По каждой: id, severity, CWE, title, автор/дата/комментарий исходного SAST-решения. |
| **Anomalies** (аномалии) | Технические инциденты (агент не записал результат, сработал safety-net и т.п.). В норме пусто. |

## 10. После прогона

```bash
# 1. Прочитать отчёт
cat sast-report-<runId>.md

# 2. Посмотреть, что накоммитили
git log --oneline <ветка-источник>..HEAD

# 3. Просмотреть diff'ы каждого фикса
git show <commit>

# 4. Если всё ок — пушим и открываем MR
git push -u origin sast-fix/<commit>-<runId>
```

Сам файл `sast-report-<runId>.md` **не входит** в коммиты ветки — это намеренно. Можно либо удалить его после ревью, либо приложить вручную к описанию MR.

## 11. Что делать, если

- **`/sast-run` не находится в qwen** — проверьте, что `~/.qwen/commands/sast-run.md` существует и qwen перезапущен.
- **«missing tool mcp__…»** — MCP-сервер не сконфигурирован в `~/.qwen/settings.json` или путь к `dist/servers/<name>/index.js` неверный. Проверьте, что `npm run build` прошёл в `<MCP_DIR>`.
- **«SAST_API_BASE_URL is required»** — добавьте `env` в `mcpServers.sast-remediation-mcp` в settings.json и перезапустите qwen.
- **«branch sast-fix/… already exists»** — был незавершённый прогон на тот же коммит. Удалите ветку (`git branch -D sast-fix/...`) или просто перезапустите команду — `runId` генерируется по timestamp и будет другим.
- **dirty working tree на префлайте** — застешьте или закоммитьте локальные правки и запустите снова. Авто-стэша нет намеренно.
- **`build_deep_index` упал** — прогон прерывается на старте. Чините `code-index` MCP — без актуального индекса прогон считается ненадёжным.
- **Один из фиксов провалился** — это нормально, прогон продолжается. Запись попадёт в **Fix failed** в отчёте, доделывайте руками.
- **Все фиксы провалились или отчёт пустой** — проверьте секцию **Anomalies** в отчёте. Если там тоже пусто — вероятно, проблема в SAST-отчёте или в `code-index`; смотрите stderr qwen.
- **Отчёт показывает 0 confirmed/rejected, но в SAST уязвимости были** — скорее всего в SAST по ним стоит `decision.type == "notexploit"` и они ушли в **Skipped (notexploit)**. Если хотите перепроверить — запустите с `--include-notexploit`.
- **«vulnerability hash not found in report» при `--vuln`** — указанный `vulnerabilityHash` отсутствует в отчёте по этому коммиту. Проверьте список через `/sast-list --commit=<hash>`. Прогон прерывается до создания ветки и индекса.
- **`/sast-run` отдаёт устаревший отчёт** — кэш в `sast-remediation-mcp` живёт без TTL. Сбросьте через `/sast-cache-clear --commit=<hash>` (или весь — `/sast-cache-clear`) и запустите снова.
- **`/sast-list` показывает не то, что в SAST UI** — кэш мог быть получен до перезапуска скана. Сбросьте через `/sast-cache-clear --commit=<hash>` и повторите `/sast-list`.

## 12. Безопасность

- JWT-токен SAST API живёт **только** внутри `sast-remediation-mcp` и никогда не уходит в контекст агента. `repo-mcp` и `code-index` ничего о токене не знают.
- `repo-mcp` пишет только в текущее рабочее дерево; в чужие репозитории не лезет.
- Финальный отчёт — локальный markdown-файл, без сетевых эффектов.
- Push в remote и открытие MR — **всегда вручную вами**, агенты этого не делают.
